# SweepX 设计复审与剩余工作

更新日期：2026-10-05。原复审基线：`e4ce069`；本轮修改与测量见[真实垃圾扫描验证](host-junk-usability-validation-2026-10-05.json)、[扫描保留预算验证](scan-retention-validation-2026-10-05.json)和[浏览器细分验证](browser-storage-usability-validation-2026-10-05.json)。本页是当前路线图；[历史实施记录](design-review-history-2026-10-01-to-2026-10-04.md)保留原文、测量和失败记录，后续实施不再逐段追加到本页。

## 结论

最初的目标是：减少过度分包和重复设计，改善垃圾识别，补齐大文件与重复文件分析，尤其解决“有缓存仍慢”，并为动态展示、选择、刷新和回收提供独立于 CLI 的能力。

**主要功能已补齐，扫描速度和垃圾识别的可用程度仍未达到完整验收。** 不能因为基础设施修复和测试数量增加，就把最初目标算作完成。

当前优先级按用户最新要求改为**真实垃圾识别、可回收结果和扫描体验**。本机已识别 187 项，实际回收 5 个缓存目录及 62 个 kaboo-cli 旧安装；修复 npm/pnpm 漏报、宽目录句柄耗尽、详情内存增长及浏览器状态误入批量删除。仍不能称为无遗漏全盘扫描或普遍热扫提速；资源审计只跟随这些入口暴露的实际问题，不再作为产品工作的前置条件。

## 当前缓存究竟加速什么

- 三平台垃圾 TUI 可以先展示历史结果。历史行不能作为当前事实或回收授权。
- 当前垃圾结果每次都现场遍历目录、规则标记和候选。旧的整根候选回放已撤回；空事件历史不能证明整棵树没有刚发生的变化。
- macOS FSEvents 可在下次运行时查询系统保留的变更历史，无需 SweepX 一直运行；历史缺口或覆盖不明时回退现场观察。持续订阅、触发局部重扫的通用监听会话尚未实现，`status --watch` 只是已有状态回放。
- macOS 文件索引可以辅助复用逻辑长度，但仍须匹配本次原生枚举的类型、长度及有效变更历史。Linux/Windows 尚无同等的文件索引复用资格，继续现场观察。
- 因此，“看到历史首屏”“文件索引有复用”和“完整扫描更快”是三个不同结果。当前 `rootCacheHits=0` 是有意保留的机器语义，不能据此判断所有缓存失效。

以下测量日期、构建、范围不同，不能直接互相比倍数。

| 测量 | 已测结果 | 能支持的结论 |
| --- | --- | --- |
| [2026-10-03 完整垃圾扫描](fresh-junk-traversal-benchmark-2026-10-03.json)：arm64 macOS、Rust 1.98.0 dev/all-features、关闭 symbols/incremental、4 根/2,048 文件、各状态 3 次，OS cache 未控制 | 空 SweepX 缓存中位数约 113.7 ms，热扫约 115.3 ms；遍历约 50.0 → 35.5 ms，缓存准备约 2.2 → 13.7 ms | 遍历阶段减少，总耗时没有改善；也不是 HEAD 的最终性能验收 |
| [2026-10-02 真实 PTY 热扫](warm-junk-tui-audit-2026-10-02.json)：arm64 macOS、Rust 1.98.0 debug/all-features、单 target 内 8,193 文件、6 个固定场景、OS cache 未控制 | 历史首屏约 28–38 ms，当前完成约 203–224 ms；退出与终端恢复通过 | 这些场景可用；没有捕获旧停顿，不能关闭其根因或推断尾延迟 |
| [2026-10-05 本机 pnpm](host-junk-usability-validation-2026-10-05.json)：arm64 macOS 26.5.2、Rust 1.98.0 release、一个真实约 5.56 GiB 逻辑长度目录、3 组独立空/热 SweepX 状态；OS cache 和宿主其他活动未控制 | 结果事实配对相同；墙钟中位数 7.178 → 6.698 秒 | 有限的改善；没有普遍热扫或尾延迟结论。另一次系统空状态/热扫为 70.214/61.066 秒，但存在并发诊断及 5 项大小变化，只作操作记录 |

早期文档中的约 21–23 ms 整根命中依赖后来撤回的回放路径，**不是当前性能承诺**。多根缓存准备的显著改善也是阶段微基准，不能代替完整扫描测量。旧 300 ms/2 s 工具探测、单大根热缓存终端偶发停顿与 FSEvents 投递问题继续单列，不能用“本次通过”关闭。

## 设计上还需要精简什么

**优先精简重复流程，暂不继续合包。** 17 个 crate 中，原生平台、遍历聚合、可丢弃缓存、规则、内容分析、呈现和执行安全仍承担不同契约。删除边界或把它们合成一个大包，不能自动降低扫描成本。

已核对的具体问题：普通 CLI 的 `run_junk_scan` 与 core 的垃圾会话都组织格式观察、Git 解释和缓存发布；它们调用相同下层组件，但编排仍有两份。普通垃圾命令的历史发布仍主要绑定 macOS，而会话已接入 Linux/Windows 历史存储。后续 CLI 重构应统一这些行为及最终状态，避免再次实现分类、缓存规则或删除判断；在现有 crate 内完成即可。

另一类复杂度来自为未知配置、所有平台和未来执行模式不断补充证明。应为支持的工具/配置定义明确范围，范围外保留 unknown/report-only。已有安全修复保留；更广 Permanent、通用插件执行器、完整生态语言求解等扩展应作为独立议题，不自动成为本轮扫描体验的完成条件。

## 剩余工作与顺序

下面五项是当前有限的待办。每次交付更新其状态和证据链接，不再新增一段“下一步”叙事。

### R1：跟随真实扫描修复现有入口的资源问题

范围限于普通 scan、junk、现有 TUI、大文件和重复文件中实际暴露的增长或边界缺口，不另建审计框架。本轮 frontier 32,768 → 128 并优先深入子树；普通详情增加 128 MiB 保留估算。数据卷扫到 920,650 个普通文件后约 90.891 秒返回 partial，采样峰值约 723 MiB；权限、131,072 个汇总预算及整体内存资格仍是边界。

完成条件：有明确的覆盖/未覆盖清单；大目录、多根、连续刷新/取消和低预算压力下，测量进程内存、原生资源峰值、输出与状态增长；超限可靠显示 partial/resource_limit，保留已完成事实及旧缓存。已有 256 I/O、128 storage-owner 和状态额度只约束参与的资源，不能宣传为全进程上限。无法由本机证明的平台运行行为归入 R4，不能暗中视为通过。

### R2：用当前实现验收扫描速度和交互

固定同一宿主、release 构建和负载，覆盖小目录、单大根、多根及真实只读缓存目录；分别测空 SweepX 缓存、热缓存、即时变化、选中刷新和取消。先核对事实等价，再记录阶段、历史首屏、首次现场候选、完整结果、键盘响应和内存峰值。

完成条件：得到可复验的配对基线；主要慢场景有完整流程改善的证据；缓存更慢时减少或绕过额外工作，并证明消除对应回退。负结果保留，但不能当作提速达标。旧停顿使用有界专项诊断和任务自身进程取样，未复现记录为未复现。不得再以准备微基准、历史首屏或撤回实现的数字勾选整体提速；少量样本不推断 p95/p99。

### R3：细分常用垃圾类别并实际回收（当前优先）

常用目录继续以真实占用与可回收流程推进。npx 已有核心/CLI 的工具、实际版本、整套安装大小及显式选择；保留最高已安装版本后，本机 62 个 kaboo-cli 旧安装共约 12.96 GiB 逻辑长度已放入回收站，逐项核对原目录消失与 Trash 身份；一个链接到项目的安装保持待确认。浏览器已有完整存储键/bucket 报告、内置扩展及 Native Messaging：可导出/注册组件，扩展内扫描、按域确认清除，CLI 请求可回传处理结果；首次安装与本地更新仍需浏览器确认，未发布扩展商店。无法选单个分区/bucket，接口按 origin 与数据类型执行，不承诺清空每个已列分区，清除无回收站，仅 SweepX 还不能按域删除。用户已在 Edge 安装扩展，本地注册、实际配置扫描与计划生成通过；用户截图确认域名列表及明细展示，0.2.1 已完成 CLI 发送、扩展接收及拒绝回传。0.3.0 重做网站存储工作台（概览、搜索排序、分区明细、单一语言切换与清理确认），增加不连接本地组件的精确网站清理入口，大小保持未知；请求过期在执行前复核。前端构建产物内嵌现有 CLI，未增加 Rust crate；bundle 更新已支持 `--update` 写回固定目录，重新加载扩展即可，通信组件路径不变；实际新版安装和浏览器删除仍待验收，见[前端验证](browser-ui-validation-2026-10-06.json)。浏览器工具禁止操作扩展内部页面，后续界面操作需用户完成，见[组件验证](browser-extension-validation-2026-10-05.json)及[Edge 验收进度](browser-extension-acceptance-2026-10-06.json)。Chrome legacy 模型已有版本回收入口与专用策略配置导出；本机约 3.98 GiB 模型已在正常退出 Chrome 后回收，独立核对身份并重启浏览器；修复 Spotlight 读取父目录元数据导致的误拒绝。专用配置已安装、用户确认策略值为 1 且正常，但 SweepX 本身只导出配置，不自动安装策略。此前 npm 等四项约 30 GiB、Yarn 约 4.71 GiB 也已移入回收站；最终复核回收站为空，原因待确认，SweepX 未执行清空操作，不据移动大小推断空间释放。osdk、Playwright 版本、现有通用缓存的内容细分与 TUI 选择接入仍待推进。Cargo 既有回收限制保留，Dart/SvelteKit 暂缓。

完成条件：支持范围内有正例、误报反例、变化/活动拒绝和真实用户流程；确实具备证据的类别可以从 TUI 确认回收，无法闭合的明确保留报告限制。不能把更多名称规则或更多 report-only 行视为“可清理能力已完成”。新的 Dart/SvelteKit 工作按用户调序继续暂缓。

### R4：完成目标平台与系统回收资格

Linux/Windows 原生测试、Windows MSVC、Linux bind mount/OFD/journal/隔离、真实云 provider、三平台实际 Trash 和持续 TUI 交互分别验收。本机完整磁盘访问生效后，5 次实际 Trash 和之前挂起的集成测试通过；这是当前宿主资格，不关闭其他宿主/权限状态下的挂起问题。GNU 交叉 lint 只有编译证据。

完成条件：每项明确 passed、failed、blocked 或未运行及环境要求；故障保留回归，不能以单次现场成功消除挂起问题。最终身份检查至系统 Trash 的 pathname 替换窗口仍需明确产品边界与处置，现有 no-follow、紧邻身份重验和失败拒绝继续保留，不承诺跨平台原子回收。

### R5：为后续 CLI 重构收敛共享编排

让普通垃圾报告和交互会话复用扫描、解释、缓存发布及最终状态，保留不同输出所需的消费方式。优先解决实际行为不一致；不机械拆文件或合包，不重写已有分类器。完整 CLI 外观重构仍留给后续工作。

完成条件：同一固定输入下两种前端的当前事实、覆盖、规则摘要、错误和回收限制一致；普通报告与三平台历史存储的关系明确，TUI 的选择/刷新行为保留。
