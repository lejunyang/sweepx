# SweepX 设计复审与剩余工作

复审日期：2026-10-04。代码基线：`e4ce069`。本页是当前路线图；[历史实施记录](design-review-history-2026-10-01-to-2026-10-04.md)保留原文、测量和失败记录，后续实施不再逐段追加到本页。

## 结论

最初的目标是：减少过度分包和重复设计，改善垃圾识别，补齐大文件与重复文件分析，尤其解决“有缓存仍慢”，并为动态展示、选择、刷新和回收提供独立于 CLI 的能力。

**主要功能已补齐，扫描速度和垃圾识别的可用程度仍未达到完整验收。** 不能因为基础设施修复和测试数量增加，就把最初目标算作完成。

最近的工作确实偏向缓存存储、句柄额度、SQLite 与审计安全。这些修改解决了实际边界问题，包括庞大输出、重复保留和无界资源增长，但其中不少只提供安全基础，没有证明用户感知的扫描速度改善。后续应收尾现有入口的资源问题，回到端到端速度和可回收垃圾，不继续无限扩展基础设施。

## 当前缓存究竟加速什么

- 三平台垃圾 TUI 可以先展示历史结果。历史行不能作为当前事实或回收授权。
- 当前垃圾结果每次都现场遍历目录、规则标记和候选。旧的整根候选回放已撤回；空事件历史不能证明整棵树没有刚发生的变化。
- macOS 文件索引可以辅助复用逻辑长度，但仍须匹配本次原生枚举的类型、长度及有效变更历史。Linux/Windows 尚无同等的文件索引复用资格，继续现场观察。
- 因此，“看到历史首屏”“文件索引有复用”和“完整扫描更快”是三个不同结果。当前 `rootCacheHits=0` 是有意保留的机器语义，不能据此判断所有缓存失效。

两组最接近当前行为的测量如下；日期、构建、范围不同，不能直接互相比倍数。

| 测量 | 已测结果 | 能支持的结论 |
| --- | --- | --- |
| [2026-10-03 完整垃圾扫描](fresh-junk-traversal-benchmark-2026-10-03.json)：arm64 macOS、Rust 1.98.0 dev/all-features、关闭 symbols/incremental、4 根/2,048 文件、各状态 3 次，OS cache 未控制 | 空 SweepX 缓存中位数约 113.7 ms，热扫约 115.3 ms；遍历约 50.0 → 35.5 ms，缓存准备约 2.2 → 13.7 ms | 遍历阶段减少，总耗时没有改善；也不是 HEAD 的最终性能验收 |
| [2026-10-02 真实 PTY 热扫](warm-junk-tui-audit-2026-10-02.json)：arm64 macOS、Rust 1.98.0 debug/all-features、单 target 内 8,193 文件、6 个固定场景、OS cache 未控制 | 历史首屏约 28–38 ms，当前完成约 203–224 ms；退出与终端恢复通过 | 这些场景可用；没有捕获旧停顿，不能关闭其根因或推断尾延迟 |

早期文档中的约 21–23 ms 整根命中依赖后来撤回的回放路径，**不是当前性能承诺**。多根缓存准备的显著改善也是阶段微基准，不能代替完整扫描测量。旧 300 ms/2 s 工具探测、单大根热缓存终端偶发停顿与 FSEvents 投递问题继续单列，不能用“本次通过”关闭。

## 设计上还需要精简什么

**优先精简重复流程，暂不继续合包。** 17 个 crate 中，原生平台、遍历聚合、可丢弃缓存、规则、内容分析、呈现和执行安全仍承担不同契约。删除边界或把它们合成一个大包，不能自动降低扫描成本。

已核对的具体问题：普通 CLI 的 `run_junk_scan` 与 core 的垃圾会话都组织格式观察、Git 解释和缓存发布；它们调用相同下层组件，但编排仍有两份。普通垃圾命令的历史发布仍主要绑定 macOS，而会话已接入 Linux/Windows 历史存储。后续 CLI 重构应统一这些行为及最终状态，避免再次实现分类、缓存规则或删除判断；在现有 crate 内完成即可。

另一类复杂度来自为未知配置、所有平台和未来执行模式不断补充证明。应为支持的工具/配置定义明确范围，范围外保留 unknown/report-only。已有安全修复保留；更广 Permanent、通用插件执行器、完整生态语言求解等扩展应作为独立议题，不自动成为本轮扫描体验的完成条件。

## 剩余工作与顺序

下面五项是当前有限的待办。每次交付更新其状态和证据链接，不再新增一段“下一步”叙事。

### R1：收尾跨平台缓存与现有入口的资源审计（当前优先）

范围限于普通 scan、junk、现有 TUI、大文件和重复文件所用路径：发现、候选展开、指纹、历史/状态读写、输出和原生 helper。复用已完成的存储和句柄检查，只修这些入口中实际发现的增长或边界缺口；不为审计另建通用框架。

完成条件：有明确的覆盖/未覆盖清单；大目录、多根、连续刷新/取消和低预算压力下，测量进程内存、原生资源峰值、输出与状态增长；超限可靠显示 partial/resource_limit，保留已完成事实及旧缓存。已有 256 I/O、128 storage-owner 和状态额度只约束参与的资源，不能宣传为全进程上限。无法由本机证明的平台运行行为归入 R4，不能暗中视为通过。

### R2：用当前实现验收扫描速度和交互

固定同一宿主、release 构建和负载，覆盖小目录、单大根、多根及真实只读缓存目录；分别测空 SweepX 缓存、热缓存、即时变化、选中刷新和取消。先核对事实等价，再记录阶段、历史首屏、首次现场候选、完整结果、键盘响应和内存峰值。

完成条件：得到可复验的配对基线；主要慢场景有完整流程改善的证据；缓存更慢时减少或绕过额外工作，并证明消除对应回退。负结果保留，但不能当作提速达标。旧停顿使用有界专项诊断和任务自身进程取样，未复现记录为未复现。不得再以准备微基准、历史首屏或撤回实现的数字勾选整体提速；少量样本不推断 p95/p99。

### R3：闭合常用垃圾类别的识别与回收

先围绕已有 Cargo 产物和常用工具缓存做完整的一类：有效输出上下文、原生对象关系、内容归属、活动/共享边界，连同用户数据误报反例。已有独立 Cargo oracle 继续作为固定版本依据，避免扩大为任意配置执行。

完成条件：支持范围内有正例、误报反例、变化/活动拒绝和真实用户流程；确实具备证据的类别可以从 TUI 确认回收，无法闭合的明确保留报告限制。不能把更多名称规则或更多 report-only 行视为“可清理能力已完成”。新的 Dart/SvelteKit 工作按用户调序继续暂缓。

### R4：完成目标平台与系统回收资格

Linux/Windows 原生测试、Windows MSVC、Linux bind mount/OFD/journal/隔离、真实云 provider、三平台实际 Trash 和持续 TUI 交互分别验收。可以通过对应机器或 CI 执行；GNU 交叉 lint 只有编译证据。

完成条件：每项明确 passed、failed、blocked 或未运行及环境要求；故障保留回归，不能以单次现场成功消除挂起问题。最终身份检查至系统 Trash 的 pathname 替换窗口仍需明确产品边界与处置，现有 no-follow、紧邻身份重验和失败拒绝继续保留，不承诺跨平台原子回收。

### R5：为后续 CLI 重构收敛共享编排

让普通垃圾报告和交互会话复用扫描、解释、缓存发布及最终状态，保留不同输出所需的消费方式。优先解决实际行为不一致；不机械拆文件或合包，不重写已有分类器。完整 CLI 外观重构仍留给后续工作。

完成条件：同一固定输入下两种前端的当前事实、覆盖、规则摘要、错误和回收限制一致；普通报告与三平台历史存储的关系明确，TUI 的选择/刷新行为保留。
