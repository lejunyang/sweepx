# SweepX Cleaner Catalog

Status: implementation catalog draft, evidence snapshot 2026-08-26. This document specifies candidate discovery and recommendation policy; it does not authorize or perform deletion.

Navigation: [overall design](../DESIGN.md) · [roadmap and verification gates](ROADMAP.md) · [project overview](../README.md)

## 1. How to read this catalog

This is an extensible semantic catalog, not a list of paths to delete. A matching row may produce an explanation and, where every gate passes, a Candidate. It can never produce approval or an execution permit. The invariant is:

    observed fact != rule inference != Candidate != Plan != ExecutionAuthorization != PreflightPermit != Outcome

All locations below are discovery candidates until a live, ordinary-user, no-follow scan binds the real owner, canonical path, filesystem identity, volume or mount, object type, version, and coverage. Environment overrides and tool output are evidence, never unaudited path injection. A name such as cache, temp, old, unused, or log is not deletion evidence.

### 1.1 Fact, inference, recommendation, and uncertainty

Each row uses these labels explicitly:

| Label | Meaning |
|---|---|
| **F** | Fact directly supported by the cited official documentation, upstream source snapshot, standard, or live manager observation. Facts retain source ID, applicable version, URL, and access date. |
| **I** | Inference derived from named facts. An inference must cite its fact IDs and is never promoted to a fact. |
| **R** | SweepX product recommendation. It may be stricter than the external manager. |
| **U** | Uncertainty, unsupported platform/layout, incomplete coverage, evidence conflict, or version-sensitive behavior. Unknown is not false, zero, unreferenced, or permission to delete. |

Published explanations additionally distinguish <code>fact</code>, <code>manager_fact</code>, <code>rule_inference</code>, <code>heuristic</code>, and <code>unknown</code>. Age, mtime/atime, familiar path names, and a negative holder check are heuristics only.

Tagged evidence values use exactly <code>known</code>, <code>lower_bound</code>, <code>unknown</code>, <code>not_checked</code>, or <code>unsupported</code>; a missing field, null, -1, or zero must not stand in for one of those states. Provenance uses <code>LiveObservation</code>, <code>ValidatedCache</code>, <code>DerivedFromCurrent</code>, <code>StalePreview</code>, or <code>Unknown</code>. Only current-generation <code>LiveObservation</code> can trigger Candidate qualification. <code>DerivedFromCurrent</code> may contribute only when every input is current live evidence; a same-generation token-validated <code>ValidatedCache</code> field may enrich an Explanation or current aggregate but cannot qualify a Candidate in v1. Imported, stale, remote, and cache-only data are display-only.

### 1.2 Side-effect classes for discovery and manager commands

| Class | Contract |
|---|---|
| <code>Z0</code> | Read existing filesystem metadata/configuration only; do not start the ecosystem CLI. This is the default scan mode. |
| <code>Z1</code> | Guarded semantic query in a disposable profile/sandbox, with fixed executable identity and argv, network denied, writes monitored, bounded output/time, and explicit user opt-in. It may still write disposable state. |
| <code>Z2</code> | Potentially stateful query: may start a daemon, download a wrapper/plugin/artifact, refresh metadata, migrate state, or write logs. Never run automatically; report that it is available. |
| <code>M</code> | Mutation such as clean, prune, remove, uninstall, wipe, repair, stop, switch, or policy update. In this catalog it describes an external official capability only. |

An official command named list, status, verify, or dry-run does not by itself prove Z0. Normal Cleaner packages cannot execute M actions. A future first-party manager adapter may execute one only if it has an exact structured dry-run/object set and scope digest; it then creates a separate Permanent R4 plan. Without that contract, the catalog emits <code>managerPermanentRecommendation</code> only. Manager-only rows must never fall back to raw directory deletion.

### 1.3 Risk tiers

Risk is monotonic and expresses approval policy, not a safety guarantee.

| Tier | Minimum meaning | Allowed outcome |
|---|---|---|
| **R1** | A local ordinary file, complete live coverage, stable identity/volume, no link, boundary, sharing, or holder signal, and strong regeneration evidence. | May be proposed for Trash after review. A directory is not R1 merely because it contains R1 files. |
| **R2** | A directory or batch, recent/user content, shared-download cache, cold-start/download cost, hard-link or reclaim uncertainty. | Trash only, with exact item list, side effects, recovery, and plan fingerprint. |
| **R3** | Executable/app bundle, database, package/container/VM state, browser application state, active log, observed-open object, cloud/provider/network/removable data, cross-volume behavior, or materially incomplete evidence. | Default skip/report; policy may allow an individually selected Trash-only item. Some factors block outright. |
| **R4** | Any proposed Permanent filesystem action, irreversible manager/browser mutation, or destructive reset. Artifact sensitivity alone does not create an executable R4 route. | Separate Permanent batch and typed ExecutionAuthorization: HumanApproval through a first-party native review surface or trusted-terminal challenge fallback, or explicit `--dangerously-delete` for an existing plan. Credentials, user state, and unique release artifacts remain R3/report-only or BLOCKED unless a separately designed action exists. Never means secure erase. |
| **BLOCKED** | Root/protected path, mount root, unknown reparse/special type, identity/containment failure, incomplete directory, elevated runtime, tampered/stale plan, or new descendant. | No action; cannot be approved or forced. |

Permanent always raises the action to R4. Directory, hard-link uncertainty, or unknown reclaimability can only maintain or raise risk. A Cleaner cannot lower core risk or emit <code>safeToDelete=true</code>.

A range such as <code>R2–R3</code> summarizes fact-dependent outcomes before discovery; every runtime Candidate and Plan must carry one exact tier after monotonic raises. Artifact sensitivity is classified independently from action risk: credentials, user state, unique release output, and protected content remain R3/report-only or BLOCKED in v1, while a separately designed irreversible action would be R4. <code>BLOCKED</code> is never one side of a runtime range and has no approval path.

### 1.4 Stable dispositions and actions

| Disposition | Meaning | Compatible action |
|---|---|---|
| <code>report_only</code> | Explain/measure only: unsupported/unknown ownership, running/shared state, sensitive R3 content, a future R4 action without an enabled adapter, missing recovery evidence, or no exact supported mechanism. | <code>report</code> |
| <code>eligible_with_confirmation</code> | Evidence permits an exact candidate, but human review and all core gates remain mandatory. | <code>filesystemTrash</code>, or a non-executable manager recommendation |
| <code>low_risk_candidate</code> | Strongly bounded, regenerable, non-shared item. This label is not synonymous with R1 and is not authorization. | <code>filesystemTrash</code> |
| <code>manager_gc_candidate</code> | The owner exposes reachability/lease/usage-aware cleanup. SweepX describes that operation and its exact scope. | Normally <code>managerPermanentRecommendation</code>; never raw deletion |

The only stable action names are <code>report</code>, <code>filesystemTrash</code>, and <code>managerPermanentRecommendation</code>. The last is advice, not execution capability.

### 1.5 Canonical row and evidence schema

Every catalog entry expands to the following versioned envelope inherited from the canonical specification and Cleaner interface contract [CAT-SPEC, IFACE-SCHEMA]; the tables below are reviewable summaries of it.

~~~yaml
schema: sweepx.cleaner-catalog-entry/v1
id: org.sweepx.<family>.<object>
title: human-readable title
artifactClass: regenerable-output | shared-store | installed-environment |
               toolchain | application-cache | application-state |
               log | diagnostic | user-data | system-state
platforms:
  - os: windows | macos | linux
    support: supported | candidate | unsupported
    rootRef: typed-known-folder | admitted-scan-root | decoded-config |
             verified-manager-output | verified-browser-profile
    locations: []
target:
  owner: manager-or-application
  grouping: object | directory | manager-scope | storage-key
  granularity: exact atomic unit
discovery:
  effectClass: Z0 | Z1 | Z2 | M
  semanticReadOnly: true | false | unknown
  zeroWriteVerified: true | false | unknown
  versionRange: explicit
  unknownVersionBehavior: report_only | block
evidence:
  required: [owner, canonical-path, identity, type, volume-or-mount,
             complete-coverage, references, activity, activation,
             official-state, running-blockers, sharing, recoverability]
  optional: []
  exclusions: []
sizes:
  logical: tagged-value
  allocated: tagged-value
  exclusiveReclaimable: tagged-value
decision:
  riskFloor: R1 | R2 | R3 | R4
  monotonicRaises: []
  disposition: report_only | eligible_with_confirmation |
               low_risk_candidate | manager_gc_candidate
  supportedAction: report | filesystemTrash | managerPermanentRecommendation
  targetGranularity: exact object scope
explanation:
  facts: [{id, claim, sourceIds: []}]
  inferences: [{id, claim, dependsOnFactIds: []}]
  recommendations: []
  uncertainties: []
references: [{sourceId, versionOrCommit, url, accessed}]
~~~

Root resolution accepts only typed sources already admitted by core. Rules use bounded typed predicates; unknown fields evaluate to unknown and follow <code>raise_risk</code>, <code>report_only</code>, or <code>block</code>. Rules contain no arbitrary scripts, shell fragments, downloads, install hooks, path concatenation, unbounded regex, or deletion adapter. Platform variants and target versions are independently declared and tested.

### 1.6 Gates shared by every row

Before any filesystem Trash proposal, all of the following are required: current local live scan; ordinary-user runtime; complete directory aggregate; canonical owner/path and stable parent/object/mount identity; no-follow and same-mount containment; no protected root/file/marker/SweepX/Trash overlap; no unknown reparse or special object; recovery conditions met; exact grouping/granularity; no active writer/manager/browser/build process; and a fresh recheck immediately before one platform action. A negative holder observation never authorizes deletion.

Trash uses Windows IFileOperation, macOS FileManager trashItem, or Linux GIO/freedesktop-compatible behavior. Unsupported Trash leaves the source unchanged; it never falls back to Permanent. Trash does not imply capacity was released or recovery is guaranteed. The executor never empties Trash. Permanent is a new R4 plan and is not secure erase.

## 4. Browser profile, site-storage, and local-model catalog

Browser state is always keyed by exact product, full version, channel, User Data/config root, logical profile/store identity, persistent root, separate cache root, adapter/source version, and observation time. A hostname is not a storage identity. The minimum attribution key is browser-specific but must preserve origin plus top-level/client site, container/private attributes, partition and bucket where present.

In every browser table, discovery/location and supported browser behavior are **F**; storage grouping and cross-store relationships are **I**; risk/disposition/recovery policy is **R**; and the final **U** clause is retained uncertainty. Every source ID resolves to a URL in section 6.3, whose access date is 2026-08-26.

Running profiles are not mutated. Lock files are clues, not proof: inspect product-specific lock ownership plus process/open-handle coverage without creating/removing locks or notifying/terminating the browser. If quiescence or layout is not verified, return <code>skipped_running_profile</code> or <code>unsupported_layout</code>. Any state snapshot must include the complete consistency group (SQLite DB with WAL/SHM/journal; LevelDB CURRENT/MANIFEST/log; blobs/bodies; quota/origin metadata; Service Worker registration/scripts/cache) at one time. Even that is not a transaction across browser stores.

## 5. Cross-row conflicts, gaps, and conservative resolutions

1. **Manager cleanup versus v1 execution.** Many official commands can clean or uninstall, while the Cleaner schema permits ordinary packages only to report, propose filesystem Trash, or issue a non-executable manager recommendation. The later interface contract wins: no M command runs through a normal Cleaner; no failed manager action falls back to raw deletion.
2. **Cargo target exception is deliberate.** Cargo documents <code>cargo clean</code>, but the designed Z0 rule may Trash only a complete, verified, quiescent target directory so it remains recoverable. This does not justify Trash for shared manager stores.
3. **Linux Trash wording.** Earlier platform research mentioned a separate confirmation after unsupported cross-filesystem Trash. The stricter safety design controls: return to Candidate, create a new Permanent R4 plan, and obtain a new exact ExecutionAuthorization—never inline fallback.
4. **No universal system/app rule.** The representative VS Code/JetBrains/Teams/Slack/Zoom/Steam/Adobe/Spotify matrix closes the product-level research gap but does not create a generic path rule. Each executable Cleaner still needs exact OS/app/version ownership, configured-root, consistency, quiescence and recovery fixtures; unknown versions and mixed roots stay report-only.
5. **System-cleaner tension.** System and package-state roots are hard protected while the product requirement asks to analyze them. v1 may scan/explain within ordinary-user visibility, but raw cleanup remains BLOCKED; only a future narrowly scoped manager adapter could mutate them.
6. **No universal liveness proof.** No manager can account for every user, project, branch, VM, container, remote builder, CI worker, offline disk or moved project. Coverage scope is always shown; no-reference-found is not unused.
7. **No universal reclaimable-byte proof.** Hard links, clones/reflinks, snapshots, dedup, overlay/CAS layers, quota and Trash make logical/allocated/exclusive-reclaimable different. Unknown or lower-bound values remain tagged; manager estimates retain their semantics.
8. **Query side effects.** Gradle wrappers/tasks, Maven plugins, Go graph commands, Flutter doctor, Android sdkmanager, Xcode simctl and other status tools may initialize, download, start daemons or write metadata. Their Z2 results cannot silently qualify a Candidate.
9. **Version drift.** npm 11 npx, Cargo 1.88 GC, Dart 3.11 GC, pnpm 10/11, Bazel 9 macOS, Android host support, Xcode tooling, Chromium layouts and browser models require version checks. Unknown future versions use <code>report_only</code> or <code>unsupported_layout</code>.
10. **Browser consistency.** Hostname-only deletion conflicts with Chromium StorageKey, Firefox OriginAttributes and WebKit top/client-origin partitioning. No browser has a transaction spanning all site stores. Running or unsnapshotable profiles are skipped.
11. **Safari mapping gap.** A Safari-visible Profile is not proven to be a UUID-backed WKWebsiteDataStore. It stays logical/unresolved and UI-only without a target-version mapping adapter.
12. **Edge/Chrome model divergence.** Chrome identifiers and M154 source paths cannot be applied to Edge. Policy support, internal diagnostics, payloads, consumers and cloud fallback must be observed per product/version.
13. **Logs and diagnostics remain app-scoped.** The representative matrix identifies some vendor log roots and UI discovery surfaces, but no generic rotation/retention/upload contract exists. Only exact closed rotations/session groups with no writer or support/compliance retention may become R2; current logs, support bundles and unknown ownership remain R3.
14. **Imported artifacts.** Exported plans/reports are useful for review and audit, but never executable input. A new local live scan and all plan/authorization/revalidation gates are required.

## 7. Definition of done for a concrete Cleaner rule

A catalog family becomes a shippable rule only when all of these are true:

1. Its manifest and rule conform to <code>sweepx.cleaner-manifest/v1</code> and <code>sweepx.cleaner-rule/v1</code>, are content-addressed/signed, declare each tested OS/architecture/tool version, and choose an explicit unknown-version behavior.
2. Every factual predicate points to a source ID above or a new primary source with URL, version/commit and access date; every inference names its input fact IDs; recommendations and uncertainties remain separately typed.
3. Fixtures cover W/macOS/Linux or explicitly assert <code>unsupported</code>; configured/non-default paths, Unicode/native names, case, symlink/reparse, hard links, mount boundaries, sparse/shared storage, permissions, running processes, incomplete enumeration and version drift are tested.
4. The rule emits all evidence families and tagged byte/coverage states. It never treats unknown as zero/false or sums shared logical bytes into promised reclaim.
5. The proposal uses only the stable disposition/action enums, never invokes a shell, never expands an arbitrary environment path, never requests elevation/stops processes/changes policy, and never substitutes raw deletion for a manager/browser operation.
6. End-to-end tests prove current-live-only Candidate creation, immutable plan binding, human exact-plan approval, immediate identity/manifest revalidation, Trash-first behavior, no fallback, durable intent/outcome and reconciliation after crash.

Until those gates pass on a real target OS/version, the row remains a catalog research entry and yields <code>report_only</code>.
